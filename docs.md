# vLLM Deployment

This project runs the Qwen2.5-Coder-7B-Instruct-AWQ model with vLLM in Ubuntu
on WSL2, then provides a browser-based chat UI. The UI can be forwarded to the
Windows host's LAN address. The vLLM API itself stays on localhost.

## Components and ports

| Component | Address | Purpose |
| --- | --- | --- |
| Chat UI | Windows LAN IPv4, TCP 8000 | Browser chat interface; forwarded to the WSL UI |
| Chat UI inside WSL | `0.0.0.0:8000` | UI and proxy to the local vLLM API |
| vLLM API inside WSL | `127.0.0.1:8001` | OpenAI-compatible inference API; not exposed to the LAN |

The UI health endpoint is `/health`, and its model proxy is `/models`. The UI
uses `/chat` for chat requests. The vLLM API also provides `/health`,
`/v1/models`, and `/v1/chat/completions`.

The model is configured in `vllm_deploy/config.py`:

- Model: `Qwen/Qwen2.5-Coder-7B-Instruct-AWQ`
- Served model name: `qwen-coder`
- UI port: `8000`
- vLLM port: `8001`
- Maximum model context: 65536 tokens (required by Hermes Agent)

## Requirements

- Windows with WSL2 and an Ubuntu distribution (the scripts default to
  `Ubuntu`).
- An NVIDIA GPU and a working WSL NVIDIA driver. `nvidia-smi` must work in the
  selected WSL distribution.
- A vLLM virtual environment at `~/vllm-deploy/venv` containing Python 3.12,
  vLLM, `requests`, and `psutil`.
- For first-time Triton CUDA initialization in this WSL environment, Ubuntu's
  `libc6-dev` package is required. Install it from an elevated Windows terminal:

  ```powershell
  wsl.exe --distribution Ubuntu --user root --exec apt-get update
  wsl.exe --distribution Ubuntu --user root --exec apt-get install -y libc6-dev
  ```

- Administrator approval is needed when configuring or removing the Windows
  LAN port-forward and firewall rule.

## First-time setup

Open PowerShell in this project folder. Use `-CheckOnly` to check WSL's Python
and NVIDIA GPU visibility:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\run_deploy.ps1" -CheckOnly
```

Stage the project into the WSL-native directory `~/vllm-deploy`:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\run_deploy.ps1" -StageOnly
```

If the vLLM virtual environment has not been installed yet, run the full
installer from the staged WSL directory:

```powershell
wsl.exe --distribution Ubuntu --exec bash -lc "cd ~/vllm-deploy && python3 deploy_vllm.py"
```

This installer downloads and installs vLLM and its dependencies, downloads the
model if needed, starts a local test server, and runs its smoke and load tests.
The first install/model download can take a while and requires network access,
disk space, and sufficient GPU memory. Once the installation and model are
available, stop that installer-launched server with `stop_deploy.ps1`, then
start using the normal workflow below. The normal launcher reuses the
installed environment; it does not reinstall packages.

`requirements.lock.txt` is generated by the installer. To use a different WSL
distribution, pass the same `-Distribution <Name>` option to both PowerShell
scripts and use that distribution in the WSL commands above.

## Start the deployment

Run from the project folder:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\run_deploy.ps1"
```

The script stages the current source, starts vLLM if its health endpoint is not
already ready, verifies the served model and a real chat completion, and starts
the UI on the WSL network interface. It then configures a Windows port-forward
to the current WSL address, adds a Windows Firewall rule limited to the local
subnet, and checks the UI health endpoint through the Windows LAN address.
Approve the Administrator prompt if requested.

On success, the script prints the current addresses, for example:

```text
Hosted chat UI: http://192.168.1.6:8000
Health check:   http://192.168.1.6:8000/health
vLLM API:       http://127.0.0.1:8001 (localhost only; not exposed to the LAN)
```

Use the URL printed by the script; the Windows LAN address may change. Devices
must be on the same local network and not blocked by guest-network/client
isolation. If WSL restarts and gets a new IP address, run the start script again
to refresh the port-forward.

Options:

- `-CheckOnly`: check WSL Python and GPU visibility without staging or starting
  services.
- `-StageOnly`: copy the project to WSL and check its Python/GPU visibility
  without starting services or configuring LAN access.
- `-Distribution <Name>`: use a WSL distribution other than `Ubuntu`.

## Stop the deployment

Stop the project's matching WSL processes and remove its managed LAN access:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\stop_deploy.ps1"
```

The stop script finds this project's deployment, vLLM, UI, and tunnel
processes, terminates their child processes, and verifies that no matching
processes remain and that ports 8000 and 8001 are closed. It then removes the
Windows port-forward associated with the project's managed firewall rule and
removes that rule. Approve the Administrator prompt if requested.

Preview the processes that would be stopped without changing anything:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ".\stop_deploy.ps1" -WhatIf
```

Stopping the project releases its model's GPU memory. It does not power off the
GPU, shut down WSL, delete the installed model, or remove the Python
environment. Unrelated applications and firewall/port-forward rules not
created for this project are left alone.

## LAN access and security

The chat UI has no user login. The UI allows up to 10 chat requests per IP per
60 seconds, but that is not authentication. Anyone on the allowed local subnet
who can reach the URL can submit prompts and consume GPU resources. Do not
forward port 8000 from your router to the public Internet. The vLLM API on
port 8001 binds to `127.0.0.1` and is not forwarded by the deployment script.

The scripts create a Windows Firewall rule named
`vLLM chat UI LAN (local subnet only)`. Removing that rule with Windows tools
outside `stop_deploy.ps1` may leave a port-forward entry behind; the stop script
intentionally avoids deleting unowned port-forward entries.

## Logs and troubleshooting

Logs are in the staged WSL directory `~/vllm-deploy`:

- `vllm.log`: vLLM startup, model loading, and inference errors.
- `ui.log`: chat UI startup and request logging.

Common checks:

1. Run `run_deploy.ps1 -CheckOnly` and confirm `nvidia-smi` lists the GPU.
2. Confirm `~/vllm-deploy/venv/bin/python` and
   `~/vllm-deploy/venv/bin/vllm` exist in WSL.
3. If Triton reports a missing `libc_nonshared.a`, install `libc6-dev` using
   the commands in [First-time setup](#first-time-setup).
4. If the Windows LAN health check fails, rerun the start script and approve
   its Administrator request. Confirm the device is on the same non-guest
   subnet.
5. To confirm the UI is stopped, check that
   `http://<Windows-LAN-IP>:8000/health` is unreachable after running the stop
   script.

Do not share `.env`, `.api_key`, or logs containing credentials or other
secrets.

## Project layout

```text
.
├── README.md                 # Quick start
├── docs.md                   # Full setup and operations guide
├── run_deploy.ps1            # Stage, start, verify, and publish the UI to LAN
├── stop_deploy.ps1           # Stop project processes and remove LAN access
├── deploy_vllm.py            # Full install, benchmark, and keep-alive workflow
├── test_server.py            # Standalone chat UI entry point
├── requirements.lock.txt     # Frozen Python dependencies
└── vllm_deploy/
    ├── config.py             # Model, ports, paths, and environment
    ├── launch.py             # Normal idempotent startup and inference check
    ├── stop.py               # Project-scoped process shutdown and verification
    ├── server.py             # vLLM process lifecycle
    ├── ui_server.py          # Browser UI, proxy, and rate limiting
    ├── installer.py          # uv and vLLM installation
    ├── benchmark.py          # Smoke and concurrent load tests
    ├── system_check.py       # Python, GPU, and compiler checks
    ├── api_key.py            # Local API-key generation/persistence
    ├── keepalive.py          # Optional heartbeat helper
    ├── tunnel.py             # Optional Cloudflare tunnel helper
    └── runner.py             # Shared subprocess helpers
```

Local-only files such as `.env`, `.api_key`, `venv/`, Python bytecode,
`cloudflared`, the bundled GCC Debian package, and runtime logs are ignored by
`.gitignore`. Keep credentials out of source control.
